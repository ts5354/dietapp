# Database Design

## 1. Purpose

This document defines the MVP database design for the mobile health logging application.

The application records:

- daily nutrition status
- individual food logs
- daily weight
- symptom logs
- injection records

The MVP is single-user and does not include authentication.

---

## 2. Global Rules

### Primary keys

All tables use:

```sql
id BIGINT PRIMARY KEY
```

IDs are generated by PostgreSQL.

### User scope

The MVP does not include a `users` table or `user_id`.

Multi-user support may be added later by introducing a `users` table and foreign keys.

### Date and time

- Event timestamps use `TIMESTAMPTZ`.
- API values are exchanged in ISO 8601 format.
- Flutter converts timestamps to the device local timezone for display.
- Day-level fields such as `nutrition_days.date` use `DATE`.

### Deletion

The MVP uses hard delete only.

No `deleted_at` column is used.

### Audit timestamps

All tables include:

```sql
created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
```

The FastAPI backend manages these values.

- On create: set both to the current time.
- On update: update only `updated_at`.
- Flutter must not provide these values.

### Memo fields

All memo fields use:

```sql
VARCHAR(500) NULL
```

## 3. Tables

## 3.1 nutrition_days

Represents the nutrition state for one calendar day.

A missing row means `UNRECORDED`.

```text
nutrition_days
- id BIGINT PRIMARY KEY
- date DATE UNIQUE NOT NULL
- mode VARCHAR NOT NULL
- memo VARCHAR(500) NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
```

### mode

Allowed values:

- `NORMAL`
- `FREE_DAY`

Constraint:

```sql
CHECK (mode IN ('NORMAL', 'FREE_DAY'))
```

`UNRECORDED` is not stored as a value. It is represented by the absence of a `nutrition_days` row for the target date.

### Rules

- One row maximum per calendar date.
- A `FREE_DAY` represents a day where calorie/protein calculation is intentionally not performed.
- `FREE_DAY` is not equivalent to `0 kcal`.
- Daily calorie/protein totals for a `FREE_DAY` are treated as not applicable.
- A day that already has one or more `food_logs` cannot be changed to `FREE_DAY`.
- When `mode = FREE_DAY`, new `food_logs` cannot be created.

The last two rules are enforced in FastAPI domain/application logic.

---

## 3.2 food_logs

Represents one eating event.

Each food entry is an independent record. Breakfast, lunch, dinner, and snacks are not stored as separate meal entities.

```text
food_logs
- id BIGINT PRIMARY KEY
- nutrition_day_id BIGINT NOT NULL
- name VARCHAR(100) NOT NULL
- calories INTEGER NOT NULL
- protein_g NUMERIC(6,2) NOT NULL
- eaten_at TIMESTAMPTZ NOT NULL
- memo VARCHAR(500) NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
```

### Foreign key

```sql
FOREIGN KEY (nutrition_day_id)
REFERENCES nutrition_days(id)
ON DELETE CASCADE
```

### Numeric constraints

```sql
CHECK (calories >= 0)
CHECK (protein_g >= 0)
```

### Rules

- Multiple records per day are allowed.
- Duplicate food name/calorie/protein combinations are allowed.
- `name` must not be empty or whitespace-only.
- The local date derived from `eaten_at` must equal the parent `nutrition_days.date`.
- A food log cannot be created when the parent nutrition day is `FREE_DAY`.

The local-date and `FREE_DAY` rules are enforced by Flutter and FastAPI, with FastAPI as the authoritative validation layer.

### Default ordering

Within one day:

```sql
ORDER BY eaten_at ASC, id ASC
```

## 3.3 weight_logs

Represents one weight record per calendar day.

```text
weight_logs
- id BIGINT PRIMARY KEY
- record_date DATE UNIQUE NOT NULL
- weight_kg NUMERIC(4,1) NOT NULL
- recorded_at TIMESTAMPTZ NOT NULL
- memo VARCHAR(500) NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
```

### Constraint

```sql
CHECK (weight_kg > 0)
```

### Rules

- Only one weight record is allowed per day.
- Incorrect input is corrected using `UPDATE`, not by inserting another record.
- `record_date` identifies the calendar day.
- `recorded_at` stores the actual measurement/recording timestamp.

### Default ordering

```sql
ORDER BY record_date DESC
```

---

## 3.4 symptom_logs

Represents a symptom observation at a specific time.

```text
symptom_logs
- id BIGINT PRIMARY KEY
- recorded_at TIMESTAMPTZ NOT NULL
- nausea SMALLINT NOT NULL
- abdominal_pain SMALLINT NOT NULL
- fatigue SMALLINT NOT NULL
- appetite SMALLINT NOT NULL
- bowel_condition VARCHAR NULL
- memo VARCHAR(500) NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
```

### Symptom scale

All four numeric fields use a 1-10 scale:

```sql
CHECK (nausea BETWEEN 1 AND 10)
CHECK (abdominal_pain BETWEEN 1 AND 10)
CHECK (fatigue BETWEEN 1 AND 10)
CHECK (appetite BETWEEN 1 AND 10)
```

Interpretation:

- larger `nausea` means stronger nausea
- larger `abdominal_pain` means stronger abdominal pain
- larger `fatigue` means stronger fatigue
- larger `appetite` means stronger appetite

### bowel_condition

Nullable.

Allowed values when present:

- `NORMAL`
- `CONSTIPATION`
- `DIARRHEA`
- `OTHER`

Constraint:

```sql
CHECK (
  bowel_condition IS NULL
  OR bowel_condition IN (
    'NORMAL',
    'CONSTIPATION',
    'DIARRHEA',
    'OTHER'
  )
)
```

### Rules

- Multiple symptom logs per day are allowed.
- Multiple symptom logs with the same `recorded_at` value are allowed.

### Default ordering

```sql
ORDER BY recorded_at DESC, id DESC
```

---

## 3.5 injection_records

Represents one injection record per calendar day.

The application records clinician-directed information only and must not recommend or automatically change medication dosage.

```text
injection_records
- id BIGINT PRIMARY KEY
- record_date DATE UNIQUE NOT NULL
- injected_at TIMESTAMPTZ NOT NULL
- dose_mg NUMERIC(5,2) NOT NULL
- injection_site VARCHAR NOT NULL
- memo VARCHAR(500) NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
```

### Dose

The unit is always milligrams and is encoded in the column name.

No separate `unit` column is used.

Constraint:

```sql
CHECK (dose_mg > 0)
```

### injection_site

Allowed values:

- `ABDOMEN_UPPER_RIGHT`
- `ABDOMEN_LOWER_RIGHT`
- `ABDOMEN_UPPER_LEFT`
- `ABDOMEN_LOWER_LEFT`
- `THIGH_RIGHT`
- `THIGH_LEFT`

Constraint:

```sql
CHECK (
  injection_site IN (
    'ABDOMEN_UPPER_RIGHT',
    'ABDOMEN_LOWER_RIGHT',
    'ABDOMEN_UPPER_LEFT',
    'ABDOMEN_LOWER_LEFT',
    'THIGH_RIGHT',
    'THIGH_LEFT'
  )
)
```

### Rules

- Only one injection record is allowed per day.
- Incorrect input is corrected using `UPDATE`.
- `record_date` identifies the calendar day.
- `injected_at` stores the actual injection timestamp.
- The next injection date is not stored in the database.
- The application calculates the next scheduled date from the most recent injection record.

### Default ordering

```sql
ORDER BY injected_at DESC, id DESC
```

## 4. Relationships

```text
nutrition_days 1 ---- N food_logs
```

Foreign key:

```text
food_logs.nutrition_day_id
    -> nutrition_days.id
    ON DELETE CASCADE
```

The other MVP tables are independent because the MVP does not use a `users` table.

---

## 5. Indexes

Create the following indexes:

```sql
CREATE INDEX ix_weight_logs_recorded_at
    ON weight_logs (recorded_at);

CREATE INDEX ix_food_logs_nutrition_day_eaten_at
    ON food_logs (nutrition_day_id, eaten_at);

CREATE INDEX ix_symptom_logs_recorded_at
    ON symptom_logs (recorded_at);

CREATE INDEX ix_injection_records_injected_at
    ON injection_records (injected_at);
```

Do not create redundant explicit indexes for:

- `nutrition_days.date`
- `weight_logs.record_date`
- `injection_records.record_date`

Their `UNIQUE` constraints already create supporting unique indexes in PostgreSQL.

---

## 6. Validation Responsibilities

### Database

The database guarantees:

- primary key integrity
- foreign key integrity
- one `nutrition_days` row per date
- one weight record per date
- one injection record per date
- numeric ranges
- enum-like allowed string values
- required/non-null fields
- cascading deletion of food logs when a nutrition day is deleted

### FastAPI

FastAPI is the authoritative layer for rules that are difficult or inappropriate to express as simple database constraints.

It must validate:

- `food_logs.name` is not empty or whitespace-only
- enum-like request strings are valid
- `eaten_at` local date matches `nutrition_days.date`
- food cannot be added to a `FREE_DAY`
- a `NORMAL` day with existing food logs cannot be changed to `FREE_DAY`
- `created_at` and `updated_at` are server-managed

### Flutter

Flutter should perform equivalent user-facing validation where useful, but backend validation remains authoritative.

---

## 7. Out of Scope for MVP

The initial database does not include:

- `users`
- authentication/session tables
- notifications
- water logs
- food database/master data
- barcode data
- AI-generated analysis
- clinician sharing
- Apple Health / Health Connect synchronization
- soft delete
- offline synchronization metadata
- `next_injection_at`
